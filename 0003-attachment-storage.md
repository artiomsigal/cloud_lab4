# ADR 0003. Хранение вложений пользователей

## Статус

Принято.

## Контекст

Приложение TimeCapsule должно хранить пользовательские вложения, обеспечивать их загрузку, скачивание и удаление. Необходимо обеспечить приватность файлов, защиту от случайного удаления, контроль расходов и возможность масштабирования приложения.

## Рассмотренные варианты

| Вариант | Преимущества | Недостатки |
|---|---|---|
| Amazon EBS | Простая работа с локальной файловой системой, низкая задержка. | Диск привязан к зоне доступности; обычная конфигурация не обеспечивает общего хранилища для нескольких серверов. Необходимо управлять ёмкостью и резервным копированием. |
| Amazon EFS | Общая файловая система для нескольких серверов EC2, поддержка привычных файловых операций. | Необходимы сетевые подключения и монтирование файловой системы; стоимость зависит от хранения и выбранного режима работы. |
| Amazon S3 | Общее объектное хранилище, независимое от серверов приложения, версионирование, правила жизненного цикла и подписанные URL. | Нет обычной файловой системы; требуется работа через API, учитываются расходы на запросы, хранение и передачу данных. |

## Решение

Использовать приватный бакет Amazon S3 `timecapsule-dev-uploads-<nickname>` в регионе `eu-central-1`. Вложения хранить под префиксом `uploads/`, а в базе данных приложения хранить ключи объектов и необходимые метаданные. Сервер `app-server` обращается к S3 с временными учётными данными IAM-роли, без постоянных ключей доступа. Разрешения ограничиваются необходимыми операциями над вложениями, включая `s3:PutObject`, `s3:GetObject` и `s3:DeleteObject`. Окончательное удаление версий (`s3:DeleteObjectVersion`) приложению не разрешается. Публичный доступ заблокирован, используется SSE-S3, политика бакета запрещает HTTP.

## Последствия

Пользователь запрашивает вложение у приложения. После проверки прав приложение формирует подписанный URL для операции GET. Браузер скачивает файл непосредственно из S3 по HTTPS. Срок действия ссылки ограничивается заданным временем и сроком действия временных учётных данных IAM-роли, если он заканчивается раньше. Ссылка не требует отдельной авторизации в AWS, поэтому её необходимо защищать от передачи посторонним.

Версионирование защищает от случайного удаления и перезаписи: обычное удаление создаёт Delete marker, а предыдущие версии сохраняются. Запрет окончательного удаления версий для приложения снижает риск необратимой потери данных. Правило `timecapsule-dev-noncurrent` действует только на `uploads/`: неактуальные версии подходящего размера переходят в Standard-IA через 30 дней, через 90 дней удаляются старые неактуальные версии, кроме двух самых новых, а незавершённые multipart-загрузки прерываются через 7 дней. Это ограничивает рост расходов на историю и незавершённые загрузки, но не устанавливает абсолютный предел стоимости хранения.

При появлении нескольких серверов приложения и балансировщика нагрузки все серверы смогут обращаться к одному бакету с одинаковыми ограниченными IAM-разрешениями. Не потребуется синхронизировать локальные диски или переносить вложения между серверами. Любой сервер сможет выдать подписанный URL после проверки прав пользователя, а скачивание будет происходить напрямую из S3, минуя балансировщик. Метаданные вложений должны быть доступны всем экземплярам приложения через общую базу данных. Таким образом, масштабирование вычислительных ресурсов не требует изменения способа хранения вложений.
